一、本版目标
------------
修掉 0.3.6 原地升级留下的两个“升级之后无路可走”的残留风险：
  RISK 1  dpkg 在 preinst 与 postinst 之间中断（典型是载荷解包失败）时，dpkg 会调用**新包**的
          `postrm abort-upgrade <旧版本号>`，而 0.3.6 对它是刻意的 no-op，于是服务可能停在停止状态、
          快照留在磁盘上。
  RISK 2  “升级失败/表现不对”时没有任何受支持的回退通道：dpkg 降级会被 preinst 拒绝
          （旧包的运行时白名单不可能认识新版本的哈希），0.3.6 之前的包更是直接拒绝 upgrade。

二、RISK 1：postrm abort-upgrade / abort-install
-----------------------------------------------
新增处理（package_lifecycle.py: postrm_abort），dpkg 调用顺序不变：preinst upgrade（快照+有界停止）
→ 解包失败 → postrm abort-upgrade <old-version>。

1. 只认“同一 boot 的未提交快照”：
   - 无 /usr/local/lib/openminis-jb-transaction → 一行 NOTICE，退出 0，零改动；
   - transaction_meta() 结构非法（schema/to_version/boot/哈希/指针/salt 任一不符）→ 一行 NOTICE，保留现场；
   - committed=true（此前 configure 已成功）→ 一行 NOTICE，不消费快照；
   - boot_stamp() 不可得，或 meta.boot != 当前 boot → 一行 NOTICE，不动；
   - 快照成员（4 个 runtime + plist + receipt）逐个 sha256 校验，**全部通过后才落盘**：
     load_snapshot() 先整体读出并校验，apply_snapshot() 才写盘 → 不会出现“改了一半”。
2. 还原内容：4 个 root 运行时文件（0644，原子 rename）→ 服务 plist（逐字节，原子）→ 所有权收据
   （仅在快照里记录时，0600；解包把它删掉时可恢复，这正是 dpkg 回滚后旧包 prerm 继续可用所需）
   → 移动端 active 指针（UID501 助手 MOBILE_RESTORE，校验 sha/版本目录存在后原子写回）→
   重启服务（必要时先 bootout）→ 认证健康检查。
3. 只依赖快照：解包可能已把 /usr/local/lib/openminis-jb 的文件删掉、截断或写成垃圾。还原路径
   先 ensure_store() 重建目录（仅在父目录 guard 通过时），再写回校验过的字节；**不读取也不复用
   解包结果**。测试覆盖 truncate（文件被截断）/ missing（目录被删）/ plist 被删 三种情况。
4. 绝不卡住 dpkg：postrm 的 shell 包装本来就 `exit 0`，本路径自身也保证不抛异常——最外层
   `except BaseException` 兜底为一行 NOTICE。所有分支都**只打印一行**（成功一行结论 / 否则一行 NOTICE）。
5. 幂等：重复执行结果相同（第二次同样校验、写回同样的字节、重启后健康）。
6. 绝不碰 token / config / audit；root 路径不导入/不执行移动端代码，移动端助手仍以 UID501 运行。
7. abort-install 走同一路径（干净安装失败时通常没有快照 → 一行 NOTICE，零改动）。

三、RISK 2：保留“上一个已知良好运行时” + root 恢复助手
-----------------------------------------------------
1. 成功升级后不再直接丢弃快照：commit() 在标记 committed 之后、删除事务之前，把**已验证**的
   升级前状态复制到 /usr/local/lib/openminis-jb-previous（root 所有 0700）：
     meta.json（0600）：schema=openminis-jb-previous-1、created、boot、from_version/from_label、
                        to_version、4 个 runtime 哈希、plist 哈希、旧 active 指针
     runtime/{launcher,maintenance_runtime,bridge,mobile_setup}.py（0600）
     plist（0600，旧 plist 原文）
   - 先整体 sha256 校验（load_snapshot）再写；先写到同父目录下的 .openminis-previous-<rand> 暂存目录，
     再用 rename 整体替换，旧目录最后删除 → 不会出现半成品；崩溃残留的暂存目录带固定前缀，
     下次会被清理。
   - 保留动作是 best effort：服务已通过健康检查，保留失败只打印 NOTICE 并**保留 committed 快照**，
     绝不因此让升级失败。
   - 第二次成功升级会用新内容整体替换保留区（“最新替换较旧”）。
   - 保留区**严格独立于 in-flight 事务**：transaction 逻辑从不读写 previous，abort 只读 transaction，
     助手只读 previous；卸载时仅当 previous_meta() 校验通过才删除，否则保留并告警。
   - 保留区不含 token/config/audit（连指纹也不含）。
2. 新增 root 可执行助手 /usr/local/bin/openminis-jb-restore-runtime（随包安装，tarball 内 0755；
   由 build.py 用同一份 package_lifecycle.py 生成，控制入口替换为 restore CLI，构建时断言
   分割点唯一且 3.9 可解析）：
     openminis-jb-restore-runtime [--dry-run] [--pointer-only]
   - 先 previous_directory()（必须 root 所有、非符号链接、0700）+ previous_meta()（结构校验）
     + load_snapshot(manifest, PREVIOUS)（逐文件 sha256），全部通过后才动手；
   - plist 形状仍用既有 equivalent() 校验（不放宽）；不符即拒绝；
   - 还原 4 个运行时文件、plist、active 指针（先停服务避免与监督器竞争），重启并认证健康检查；
     逐条打印它做了什么（dry-run 只打印计划）；
   - --pointer-only 只还原移动端指针（不动 root 运行时/plist）；
   - manifest 缺失/损坏/未知 schema/权限或类型异常、快照与 manifest 不一致 → 拒绝（退出 1）；
   - 幂等；**不读取也不打印 token**（root 侧不调用指纹助手），不写 token/config/audit；
   - 只**提示**存在 in-flight 事务，绝不读取/修改/删除它；dpkg 记录的版本与 manifest 的 to_version
     不一致时打印一行说明后继续。
3. 如实说明（已写入两个 README）：助手回到的是**设备上的旧运行时**，dpkg 仍记录**更新的包版本**
   （其文件确实安装成功）。因此**不建议**用安装旧 .deb 的方式降级（旧包白名单不认识新哈希，
   preinst 会在改动前拒绝——这正是 RISK 2 的起因），也不要用 --force-downgrade 绕过校验。
   推荐流程：先 `--dry-run`，需要时 `--pointer-only` 或完整回退，然后**重装当前/更新的正式包**
   （重装即一次正常原地升级，token/配置/审计不丢）。

  - --pointer-only：root 运行时与 plist 不变，只还原指针；

  - 0.3.6 → 0.3.7（payload 逐字节相同）场景下，回退的可见效果是 active 指针与重启。

六、未验证项（真机）
--------------------
1. 真机 `dpkg -i` 解包失败后 dpkg 调用 `postrm abort-upgrade` 的实际时序与退出码（本机测试为
   离线模拟：直接调用 postrm 实现，stdout 断言“恰好一行”，并另断言 postrm 脚本永远 exit 0）；
   建议用 ABORT_TEST_0371.md 里的演练包在设备上确认：服务恢复健康、dpkg -l 仍为旧版本、
   token/config/audit 字节不变、快照（committed=false）保留。
2. dpkg 自身的文件回滚与我们的快照还原是否会在真机上互相干扰（两者目标一致：旧运行时）——
   离线测试只能证明我们这一侧幂等且只依赖快照。
3. launchctl bootout/bootstrap 在 user/501 域的真实时序（沿用 0.3.3/0.3.5 已验证路径）。
4. 恢复助手的 --dry-run/--pointer-only/完整回退在真机上的输出（assistant 需要 root 与 jbroot 可解析；
   本机测试以 patch 提供 root 与 UID501 替身）。
5. Python 3.9 仅做语法解析（设备为 3.9.9）：本版新增代码未使用 `os.listdir(fd)` 等 3.9 语义差异点
   （保留区/事务的目录列举一律用 `os.scandir(path)`，不使用会被关闭的 fd），
   但真机仍需确认。
6. 测试为离线运行（无真机、无生产 token、无网络）；测试进程以 root 运行（fixture 需要 0700 目录），
   与 0.3.6 报告一致。
