一、本版目标与范围
------------------
0.3.3-1 的 preinst 曾以 “CLEAN-INSTALL ONLY” 明确拒绝 upgrade（要求先卸载）。本版把它替换为
**原地升级**：Sileo 直接更新即可，且**不重置 token**、不清配置/审计/版本目录。
本版**不**放宽安装语义：干净安装与卸载/清除行为与 0.3.5 完全一致
（仍然只在 dpkg 记录为 “install ok installed” 时拒绝 ‘install’ 覆盖行为，
'deinstall ok config-files' 之后的直接重装不需要 purge）。

二、升级序列（dpkg 顺序：preinst upgrade → unpack → postinst configure）
---------------------------------------------------------------------
A. preinst upgrade（旧运行时仍在原位，任何失败都在改动前中止）
 1. 完整预检：root、dpkg 架构 iphoneos-arm64e、Roothide 根映射（jbroot 校验）、
    mobile 身份/组（UID 501、无 gid 0）、STORE 与 plist 的祖先安全（guard）。
 2. 运行时白名单：读 launcher.py / maintenance_runtime.py / bridge.py / mobile_setup.py
    四个文件的 sha256，必须**整组**命中显式白名单：
      0.3.3-1（bridge ec7d5775…4b9003）
      0.3.5-1（bridge dfa21e1a…5b73f）
      本版打包集（bridge 1d64cb7f…9c385，用于同版本升级/重装）
    混合或未知组合一律拒绝（stage=upgrade-runtime-allowlist）。
    说明：0.3.2-3/0.3.2-4（launcher b905c063、bridge 425029fd）与 0.3.4-2（bridge 4bffa899）
    属于“已知但不支持原地升级”的历史版本，按老规矩先卸载再安装；如需支持，
    只要在白名单表里各加一行即可（表内有注释给出这些哈希）。
 3. plist 形状：使用既有 equivalent() 逻辑（容忍 __Patched 与路径别名）校验
    /Library/LaunchDaemons/app.openminis.jbbridge.plist。
 4. boot 身份：读取 kern.boottime（ctypes sysctlbyname，失败时退回固定候选路径的 sysctl 二进制），
    记为快照的一部分，用于拒绝跨 boot 复用。
 5. 移动端只读指纹（UID501）：校验 active 指针形状与 current 版本目录存在且哈希相符，
    并用**随机盐**计算 token / config / audit 的 sha256（盐只存在于 root 0700 事务目录内；
    token 明文既不打印也不落盘）。此时不写入任何移动端文件。
 6. 遗留快照处理：若 /usr/local/lib/openminis-jb-transaction 已存在，必须是结构有效、
    root 所有 0700、schema 匹配、to_version 匹配的目录；仅当 “committed=true”（此前升级已成功）
    或 “同 boot 且记录的 runtime/plist/active 指针与磁盘现状逐项相符” 时才删除并重拍，
    否则**拒绝且不做任何改动**（stage=upgrade-leftover-snapshot）。
 7. 快照：新建 root 0700 事务目录，写入
      runtime/{launcher,maintenance_runtime,bridge,mobile_setup}.py（逐个复核 sha256）
      plist（旧 plist 原文）
      receipt（旧所有权收据原文，仅作诊断，不参与复用判定、不回滚）
      meta.json（0600）：schema、created、boot、from_version、to_version、label、
                        四个 runtime 哈希、plist/收据哈希、移动端 active 指针、盐与三份指纹、
                        committed=false
    并 fsync 目录。**不复制 token、config、audit，也不复制 mobile 版本目录**。
 8. 停止服务：复用既有 stop()（launchctl bootout，绝不 pkill/killall），
    再以 UID501 removal('stopped()') 有界确认监听端口与监督器锁已释放
    （stage=upgrade-listener-released，默认 20s）。失败则重新拉起服务、丢弃快照并中止。

B. postinst configure（新文件已解包）
 1. 完整性：四文件必须命中打包哈希（缺失/不符即失败），plist 缺失或不符时按期望内容原子重建。
 2. 移动端对账（UID501，root 从不导入/执行移动端代码）：
    - 先用同一盐重算指纹，token/config 必须与 preinst 完全一致（不一致则**在改动前**中止）；
      audit 变化仅提示（服务自身审计是追加写）。
    - 刷新所有权收据（包自身元数据，仅此一项；使卸载在升级后仍然可用）。
    - 打包 bridge.py 的 sha 与当前 active 相同 → 什么都不做（stage=activate-mobile-reconcile,
      MOBILE_ACTIVE:unchanged）；不同 → rt.stage() 入 versions-v030/<sha>/bridge.py 后
      **一次原子 os.replace 切换 active 指针**，previous = 旧 active（jb_rollback 继续可用），
      并清掉可能残留的 trial 字段（避免监督器把 trial 版本当成激活版本）。
 3. 启动服务（指针切换过则先 bootout 再 bootstrap），校验注册与 plist 等价，再做认证健康检查
    （UID501、api 3、version/sha 一致、supervised）。
 4. 再次以同一盐核对 token/config 未变（audit 允许追加/滚动），并核对指针等于预期
    （switched 时 current=打包 sha、previous=旧 active）。
 5. 成功：meta 标记 committed=true（fsync），随后删除事务目录；
    清理失败只提示不报错（该目录已标记提交，下次 preinst 会当作过期快照处理）。
 6. 失败：回滚 → 旧 active 指针（若切换过）→ 旧 root 运行时四文件 + 旧 plist（按快照原文，
    逐文件 sha256 复核后原子替换）→ 重启旧版本并复检健康 → 以**非零状态**退出，
    并输出**唯一一条**受控失败信息（不回显异常文本、路径或任何子进程输出）。

三、失败恢复保证与边界
----------------------
保证（离线模拟的完整 dpkg 序列中逐项断言）：
 - 健康检查失败时：旧 root 运行时四文件、旧 plist、旧 active 指针全部回到升级前字节；
   服务重新注册并运行旧版本；postinst 以非零退出（REPORTED 标志 + 唯一失败行），dpkg 可正常收尾；
   token/config/audit 字节不变。
 - 白名单不符、plist 形状不符、active 版本目录缺失、遗留快照不可复用（跨 boot / 内容不符 /
   结构非法）：一律在**任何改动之前**拒绝，且不动磁盘、不停止服务。
 - 停止阶段无法确认端口释放：重新拉起服务并丢弃快照后中止，服务不会停留在停止状态。
 - 升级全程不写 token/config/audit/versions；除“指针 + 收据”外不修改任何移动端状态。

边界（明确不承诺）：
 - 若 dpkg 在 preinst 之后、postinst 之前中断（例如解包失败后 dpkg 报 abort-upgrade），
   本包按既有约定**不**在 postrm 的 abort/disappear 分支做恢复（这些分支 0.3.5 起即为空操作，
   改动它们会引入新的失败面）。此时服务可能处于停止状态，快照保留；重新执行安装/升级即可继续，
   或按提示审核后手动删除事务目录。这是本版最主要的残余风险。
 - postinst 已回滚（旧运行时回到磁盘）之后，dpkg 数据库仍记录新版本；此后 dpkg --configure -a
   会因打包哈希不符而失败（这是诚实的：文件与数据库不一致），需要重新安装本版或 purge。
 - audit 在健康检查窗口内会被服务自身追加（最多数条）；本包只保证“不重写、不清空、不重置”。
 - token/config 的“未变”通过盐化 sha256 指纹核对，不读取/不打印 token 明文。
 - 收据（.clean-install-v032 内的版本字符串）会随升级前移（包元数据，非用户数据）；因此它
   不参与快照复用判定，回滚时也不回滚。

test_upgrade.py 覆盖（完整模拟 dpkg 序列：preinst upgrade → unpack → postinst configure）：
 - 从 0.3.3-1 升级：快照内容（四文件/plist/meta/boot/指针/盐）逐项校验，服务先 bootout；
   升级后 store=打包集、指针 current=打包 sha、previous=旧 active、新版本目录写入正确、
   收据刷新为本版、事务目录已删除；token/config/audit 字节不变。
 - 从 0.3.5-1 升级：同上（并断言 label=0.3.5-1）。
 - 移动端 sha 已相同（no-op switch）：指针与版本目录数量都不变，服务仍健康。
 - 同版本升级（0.3.6→0.3.6 重装）与“连续两次升级幂等”。
 - 新鲜安装序列（preinst install → unpack → postinst configure）仍然工作（token/config/指针/收据）。
 - 健康检查失败：旧运行时、旧 plist、旧指针全部还原，服务重启旧版本，退出非零，
   只有一条失败信息，事务目录保留且 committed=false，token/config/audit 字节不变。
 - 失败后重试：遗留快照被验证后替换，第二次升级成功。
 - 未知运行时、混合运行时（0.3.2 launcher + 0.3.3 bridge）、plist 形状不符、
   active 指针指向不存在的版本目录：都在改动前拒绝（并断言磁盘/服务/状态零变化）。
 - 遗留快照：同 boot 且内容相符 → 允许替换；跨 boot → 拒绝；内容与磁盘不符 → 拒绝且原样保留；
   结构非法 → 拒绝；meta 中 salt/schema/boot/to_version 任一项被篡改 → 拒绝且原样保留；
   committed=true → 视为过期并替换。
 - 无升级事务时的 configure（例如 dpkg --configure -a）：带遗留收据且运行时为本包时，仍会对账移动端、
   启动并健康检查；只有“已识别的升级事务”才提供 root/plist 回滚能力。
 - 端口未释放导致停止失败：服务被重新拉起、快照丢弃、磁盘零变化。
 - 无快照时的 configure（旧收据 + 新运行时）：仍会尝试对账，失败时只回滚指针并保证服务在运行。
 - UID501 辅助程序本身：Python 3.9 可解析、指纹只读、打包 sha 变化时拒绝、
   指针恢复写回原值；白名单常量与两个发行集逐字节一致。

五、未验证项（真机）
--------------------
1. 真机原地升级（本版核心）尚未在设备上执行；以下依赖真机环境、无法离线证明：
   - ctypes sysctlbyname('kern.boottime') 在 Roothide 假根环境中的可用性（已加 sysctl 二进制回退）；
   - launchctl bootout/bootstrap 在 user/501 域的真实行为与端口释放时序（沿用 0.3.3/0.3.5 已验证路径）；
   - 健康检查在本版 bridge 0.3.6 上的实际结果。
2. 升级路径的 SELinux/沙箱级限制、以及 dpkg 中断（abort-upgrade）场景未做真机演练。
3. 本机测试运行在 Python 3.12；Python 3.9 仅做语法解析（device 为 3.9.9），不等同真机验收。
4. 最终定稿运行（单进程 Python 3.12 `python3 -m unittest test_package test_safety test_filetools
   test_api test_supervisor test_upgrade`）198 项全部通过、耗时 141s。
   在此之前的一次组合运行中，test_api.py 的 2 项与 test_supervisor.py 的 1 项真实进程用例曾偶发失败
   （真实端口/时序竞争：这些用例自选空闲端口并启动真实子进程）；单独运行与最终整体运行均通过，
   与本次改动无关，但仍属已知测试脆弱点。
